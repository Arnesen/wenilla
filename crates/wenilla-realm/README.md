# wenilla-realm

The realm service: one process that serves the browser client behind a login, hands each
player their (hidden) game credentials, and gives the admin a panel to run the game server.
It wraps `wenilla-host`'s routers (`/data/*`, `/ws/{port}`, the wasm files) in a session
check, so nothing the game needs is reachable without signing in — the stock client cannot
connect at all, and no game or console port has to be exposed.

Packaged for a single VM with Docker Compose in **github.com/Arnesen/wenilla-realm** (that
repo is the place to start: `realmctl up`, then `/setup`). This crate is what runs inside the
`realm` container.

## What it does

- **Login blocker.** Username + password (argon2id) for admins and players; players are
  created by an admin in the panel and must change their password at first sign-in. Sessions
  are a random cookie token hashed at rest, `Secure; HttpOnly; SameSite=Lax`, rotating.
- **Play page** (`/`). Fetches `{user, pass, host, realm}` (and `char` for a preset character) from `GET /api/play` over the session and
  boots the wasm client with `window.__wenilla_env` — the game password is generated by the
  service, kept encrypted (ChaCha20-Poly1305 under `/state/master.key`) and never shown.
- **Admin panel** (`/admin`): server status and who is online; announce/notify; restart with a
  countdown (mangosd exits 2, the container restart policy brings it back); users — create,
  ban/unban, kick, reset web password, rotate game password, role, disable, delete (with
  characters); settings — XP/loot/money rates, player limit, save interval, max level, MOTD,
  random-bot count, auction-house bot, applied live through `reload config` where the core
  allows it; an audit log of everything.
- **Dungeon presets** (`/admin/presets`, `/g/{token}`). One click makes a group of geared,
  talented, level-appropriate Alliance characters standing at an instance entrance — *The
  Deadmines* (five level-20 heroes) and *Blackrock Depths* (five level-56) — and a secret link
  for it. Whoever opens the link picks a role card ("Warrior · Tank") and is dropped straight into
  the world as that character, with no sign-up; the same page summons the group back to the
  entrance and deletes the whole group (every account and character). See *Dungeon presets*
  below.
- **Setup wizard** (`/setup`), gated by a one-time token printed at first start: admin account,
  realm name, presets. It also creates its own console account (`WRSOAP`) and re-passwords the
  seeded `ADMINISTRATOR`/`GAMEMASTER`/`MODERATOR`/`PLAYER` accounts.

## Configuration (environment)

| variable | default | meaning |
|---|---|---|
| `REALM_BIND` | `0.0.0.0:8090` | listen address (Caddy proxies to it) |
| `REALM_PUBLIC_URL` | `https://localhost` | what players open; also the only WebSocket `Origin` accepted |
| `REALM_STATE_DIR` | `/state` | `realm.sqlite`, `master.key`, `setup-token` |
| `REALM_WWW` | `/app/www` | the wasm dist (`wenilla.js`, `wenilla_bg.wasm`, `wasi_stubs.js`) |
| `CLIENT_DATA` | `/client/Data` | the operator's client `Data/` (read-only) |
| `CONFIG_DIR` | `/config` | `mangosd.conf`, `aiplayerbot.conf`, `ahbot.conf` — edited in place |
| `MARIADB_URL` | `mysql://realmweb:…@mariadb:3306/classicrealmd` | read-only game DB user (+ `UPDATE` on `realmlist`) |
| `SOAP_URL` | `http://mangosd:7878/` | mangosd's SOAP console |
| `SOAP_BOOTSTRAP_USER/PASS` | `ADMINISTRATOR`/`ADMINISTRATOR` | console login until the wizard has made `WRSOAP` |
| `REALMD_HOST`, `MANGOSD_HOST` | `realmd`, `mangosd` | where `/ws/3724` and `/ws/8085` are relayed |
| `REALM_BOOTSTRAP_TTL_HOURS` | `48` | how long an admin-issued first-login password stays usable (`0` = forever) |
| `WENILLA_DEV_QUERY_CREDS` | `0` | `1` lets `?user=&pass=` links log in (development only) |
| `REALM_COOKIE_INSECURE` | `0` | `1` drops the cookie's `Secure` flag (plain-http development only) |

### The admin-issued password is a bootstrap credential

An admin creating a user (or pressing *reset web password*) gets a generated password shown once,
to hand over out of band. That password is not an account password: it exists to get the person to
their first login. Two things enforce that, because a password pasted into a chat scrollback
otherwise stays a permanent key to a playing account:

- **The forced change is a gate, not a suggestion.** A session that still holds such a password
  reaches `/account/password` and nothing else — not `/`, not `/api/play`, `/data/*` or `/ws/*`.
- **It expires** after `REALM_BOOTSTRAP_TTL_HOURS` (default 48). A password the user chose
  themselves never expires. An expired one is refused at login with an explanation, and the
  recovery path is the admin panel's *reset web password*, which issues a fresh one with a fresh
  clock.

`wenilla-realm reset-admin` forgets the admin's password and prints a fresh setup token; the
wizard then only sets a new admin password. That is also the break-glass path if every admin's
password has expired — it needs no password at all, only shell access to the host.

## Dungeon presets

A preset is a file in `presets/` (compiled in): the level, the `game_tele` entrance, and per slot
the race, class, spells, proficiencies, talent picks, bags, gear and consumables. The files are
generated from a world database and `Talent.dbc` by `scripts/gen-realm-presets.py` (the roster
and talent picks are written in that script; the trainer spells and the best obtainable gear per
slot are queried) — change the script and rerun it rather than editing the output.

Making a group creates one ordinary player user per slot, with its own hidden game account
(named `WP` + random, never `WR<id>`, so it cannot meet an account an earlier install left), and
builds the characters in the background, all at once, in about half a minute. The service builds
each one **by playing it** (`src/presets/headless.rs`, on `benilla-protocol`): it logs in to the
fresh account, which holds GM level 3 for the duration, creates the character, and says the
dot-commands — `.levelup`, `.learn`, `.maxskill`, `.additem`, `.modify money`, `.tele` — then
equips every item with the same `CMSG_AUTOEQUIP_ITEM` a right-click sends, logs out (which saves
it) and drops GM back to 0. The world server applies and checks every step, so the service needs
no write access to the character database.

The link's token is 256 random bits, stored hashed (and encrypted, so `/admin/presets` can show
the link again). The `/g/…` routes sit outside the session layer, are rate-limited per IP, send
`no-store`/`no-referrer`/`noindex`, and joining mints an ordinary session for that slot's user —
the play page, relay and locks treat it like any invited player, and `/api/play` adds the
character's name, so the client skips the login, realm and character screens. Deleting kicks
anyone online, deletes each game account (and with it the character) and the users, which ends
their sessions. A group cannot be deleted while it is still being built; a service restart
mid-build marks it failed so it can be.

Checked against a real realm by `tests/presets_live.rs` (skipped unless pointed at one): it builds
both presets and verifies every character in the character database — level, class, position at
the entrance, every item worn, bags, talents, weapon/armor skills, GM level back to 0 — then
deletes both groups and checks nothing is left.

```bash
TEST_SOAP_URL=http://127.0.0.1:7878/ TEST_SOAP_USER=<gm> TEST_SOAP_PASS=<pass> \
TEST_MARIADB_URL=mysql://mangos:mangos@127.0.0.1:3306/classicrealmd TEST_REALMD_HOST=127.0.0.1 \
  cargo test -p wenilla-realm --test presets_live -- --nocapture   # TEST_PRESET=brd for one, TEST_KEEP=1 to keep
```

## Developing

```bash
cargo test -p wenilla-realm          # unit tests + an end-to-end pass through the router with a mock console
cargo run --release -p wenilla-realm # needs a running realmd/mangosd/MariaDB — see the env table
```

The integration test (`tests/app.rs`) drives the wizard, creates a player, signs in as them,
fetches `/api/play`, and checks that every game route answers 401 without a session and that
CSRF / cross-site posts are refused.
